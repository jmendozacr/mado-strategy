# Correction — 2026-11-26

Linked from `docs/02-results-and-report.md` (a banner was added there pointing here). This
corrects the INTERPRETATION of findings already in that report -- it does not change any
underlying count. All three review findings below were verified directly against the source
artifacts before being accepted.

## 1. Order placement vs. entry-bar timestamp -- these are two different instants, conflated in
## the original report's framing

The original report (Section E) correctly established that `order_placed_ts` (the confirmation
instant) is never after 13:00 NY: **1,308 of 1,427 executed trades have `order_placed_ts` strictly
before 13:00, 119 exactly at 13:00, zero after** -- re-verified here, unchanged.

**What was missing**: `order_placed_ts` is the instant the decision to submit an order is made --
it is NOT the instant the trade actually fills. `fill_pass_c` searches forward from the first bar
after confirmation for the first bar that touches `entry_price`, which can take multiple bars.
Checked directly against the real ledger's own `entry_timestamp_broker` (the recorded ENTRY bar,
not the order-placement instant): of the same 1,427 executed trades, the entry bar opens **before
13:00 for 1,104, exactly at 13:00 for 116, and after 13:00 for 207 (14.5%)**.

**Correction**: the original report's framing ("the order is never placed after 13:00") was true
but incomplete on its own -- it invited the reader to conclude the ENTIRE decision (including
fill) never depends on post-13:00 information, which is false for 207 trades whose actual entry
bar opens after 13:00. An entry-bar timestamp identifies a 15-minute interval (the bar's own open),
not an exact intra-bar fill instant -- this document does not claim to resolve sub-bar timing
either, only to state the bar-level fact precisely.

## 2. The `INSIDE` population includes double sweeps -- the original report did not decompose this

Of the 3,537 `INSIDE` activations, **957 (27.1%) are double sweeps (`sweep_side == "BOTH"`)**,
leaving **2,580 (72.9%) with a strictly single-sided sweep and a strictly-inside close**. The
original report's own +0.704R INSIDE-vs-OUTSIDE retrospective difference (Section C) pools both
sub-groups together without saying so explicitly. This is not a defect in the computed number
itself (the population was always "all INSIDE activations," stated correctly as such in the
funnel table) -- it is a missing decomposition that a reader could otherwise miss. Restated
plainly: **that figure describes the full INSIDE population, including the 27.1% whose
Raza-direction is itself ambiguous (`DOUBLE_SWEEP_AMBIGUOUS`).**

## 3. The claim that a prospective rule "necessarily requires a wider confirmation window" is
## replaced by a narrower, better-supported conclusion

The original report's Section F stated this as an unconditional requirement. The first
experiment's own data supports a narrower claim:

- For the 1,308 trades (91.7%) whose order places strictly BEFORE 13:00, the close-back-inside
  label genuinely does not exist yet at the decision instant -- a prospective use of it for THESE
  trades would indeed require a redesigned window (this part of the original conclusion stands).
- For the **119 trades (8.3%) whose order places EXACTLY at 13:00**, the current H4 candle's own
  close becomes final at that SAME M15-bar-resolution instant, because the confirming M15 bar
  (the one whose own close completes Model-1's retest) is the SAME bar whose own close completes
  the H4 candle itself. **These are not "the close is unavailable" cases -- they are "the close and
  the confirmation decision are the same event" cases.** Whether the close is genuinely knowable
  "before" vs. simultaneously with the order decision cannot be resolved at M15 (15-minute) data
  resolution -- this requires the explicit event-ordering check in `docs/06-session-trace.md`
  (Section 2 of the brief), not an assumption in either direction.

**Corrected conclusion**: a prospective rule does NOT necessarily require a wider window for the
ENTIRE population -- it requires one only for the ~92% of 9AM confirmations that resolve strictly
before 13:00. For the narrow subset that resolves exactly at 13:00 (`docs/06`/`docs/07`), the
close and the confirmation are informationally the same event, and a same-deadline variant is at
least representable -- subject to the ordering check resolving that it is not simultaneously
indeterminate in a way that breaks the comparison. That check is Section 2's own deliverable.
