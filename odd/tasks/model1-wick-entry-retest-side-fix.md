# model1-wick-entry-retest-side-fix

Objective: fix `entries/model1.py::_select_entry`'s wick-type entry price — it returned the anchor's protected/swept extreme (`anchor.low` bullish / `anchor.high` bearish) instead of the retest-side body boundary, contradicting both real executed trades and the already-correct, already-spec'd `backtest/levels.py::entry_price` (REQ-47.2, ADR-05).
Branch: `detector-key-level-reaction-probe`. Delivery: `ask-on-risk` — single work-unit commit.
Test runner: `cd detector && python -m pytest` with `PYTHONPATH=".;.venv/Lib/site-packages"` (Device Guard still blocks the venv's own `python.exe` this session).

## Specs

- **S1 — User-reported defect (2026-11-10, verbatim, paraphrased from the triggering message)**: "el retest A debe ser la entrada, el order limit de buy ... debería ser el high del ancla ... y el SL abajo del ancla". Investigated via a real executed GBPUSD M15 trade screenshot: anchor candle low=1.32012 (SL), high=1.32147 (confirmed by the user as the actual entry), TP=1.32592. This directly contradicted `_select_entry`'s bullish-wick formula (`anchor.low`, the swept/protected side).
- **S2 — Verification before accepting the claim.** Initial pushback (wrong, corrected with proof): re-read `docs/charter-2.md` lines 98-113 ("Reglas de Selección: ¿Cuándo usar la Mecha o el Cuerpo?") and concluded "la mecha" meant the swept side — directly contradicted by the real trade. Re-derived: the valid Model-1 retest is against the breakout edge the confirming close broke through (the side nearer the current trend, not the liquidity-sweep side far behind it) — re-testing the swept side would mean giving back the entire expansion move.
- **S3 — Cross-check against existing signed spec, before touching code.** `openspec/specs/detector/spec.md` REQ-47.2 and `openspec/changes/archive/2026-08-29-crt-detector-backtest-engine/design.md`'s ADR-05 already define, independently, a wick-entry formula for `backtest/levels.py::entry_price`: **the retest-side body boundary** (`max(anchor.open, anchor.close)` bullish / `min(...)` bearish) — grounded in charter-2, deliberately chosen, and explicitly rejecting "entry at the wick extreme" as an alternative (ADR-05's own alternatives-considered list) because that alternative, as evaluated at the time, collapsed risk to near-zero (entry coinciding with the stop's anchor point). That rejected alternative is NOT the same value this fix introduces — ADR-05 evaluated the swept-side wick tip (same point as `protected_extreme`, the stop's anchor); this fix uses the breakout-side BODY edge, which sits far from the stop, so no collapse risk applies.
  - ADR-05 also explicitly declined to change `_select_entry` to match, for a DIFFERENT reason: preserving REQ-19's already-signed detection-output fixtures at the time — a non-regression/process concern, not a claim that `_select_entry`'s own formula was correct. `backtest/levels.py::entry_price` was therefore already right all along (REQ-47.2) and is **untouched** by this fix — it only ever drove `trades.csv`/backtest P&L/the live scanner's actual fill price. The bug was isolated to `Model1Signal.entry_price` (`entries/model1.py`), which only drives `detections.csv` and the chart overlay marker (REQ-42.2 already discloses the two are independently computed, for exactly this reason).
- **S4 — Fix.** `_select_entry`'s wick-case returns now mirror REQ-47.2's own formula: `max(anchor.open, anchor.close)` (bullish) / `min(anchor.open, anchor.close)` (bearish), replacing `anchor.low`/`anchor.high`. The pre-confirmation-breach fallback in `_track_anchor` (which mirrors what `_select_entry` "would have returned" when no engulfing close ever occurred) was updated identically, for the same reason it existed in the first place.
