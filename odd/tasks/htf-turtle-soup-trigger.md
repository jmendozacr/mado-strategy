# htf-turtle-soup-trigger

Objective: new HTF-first detection pipeline — a 4H candle that Turtle-Soups the immediately preceding 4H candle WHILE its purge wick touches a registered Key Level becomes an unambiguous trigger; LTF (15m) confirmation (Model-1 + the existing retry chain) is then searched only within that trigger's own time window. Replaces the need for `causal.htf.select_htf_context`'s H-A rule (which searches ALL historical HTF ranges and picks by recency, collapsing credited signals ~78% on long history — see `odd/tasks/model1-causal-retry-chain.md` L2b) for this new pathway: there is never a search, because the trigger candle itself IS the context.
Branch: `detector-key-level-reaction-probe` (continuing this session's branch). Delivery: ask-on-risk, one work-unit commit per task.
Test runner: `cd detector && ./.venv/Scripts/python.exe -m pytest` (uv trampoline blocked in this environment). `lint-imports`: `cd detector && ./.venv/Scripts/lint-imports.exe`.

- **S1 — User's proposal (verbatim, paraphrased across two messages, 2026-11-12)**: "¿Qué pasa si el scanner o backtest lo corremos en HTF y cuando la vela de 4H toque un key level entonces pase a la siguiente fase: estoy haciendo un Turtle Soup a la vela anterior de 4H mientras estoy tocando un key level? Si es así, buscamos la confirmación en 15m con lo que tenemos." — HTF-first: detect the 4H trigger, then cascade to LTF confirmation, instead of today's LTF-first-then-backfill-HTF-context order.
- **S2 — Same-candle requirement (verbatim)**: "tiene que ser la misma [vela] porqué probablemente esa vela se vaya a expandir luego de esa manipulación" — the Turtle Soup candle and the key-level-touching candle MUST be the same HTF candle.
- **S3 — No HTF-level retry (verbatim)**: "no reintentamos porque si estamos en la sesión de NY otra vela de 4H estaríamos fuera de sesión y no es lo recomendable" — unlike the LTF retry chain (model1-causal-retry-chain), a failed HTF trigger candle does NOT retry with the next HTF candle.
- **S4 — Confirmation window is session/model-specific, not universal (verbatim + verified against the charters)**: for the 9:00 (NY) model, confirmation must be found within 1.5 hours of the 4H candle's open (09:00–10:30 NY-local), matching charter-11's documented primary window (09:00–10:00) and secondary window (09:30–10:30). Other feeder-candle models (1AM, 5AM) have their OWN documented windows in charter-8/9/10 and are explicitly OUT OF SCOPE for this first pass (see Tasks) — no charter states one universal "first N hours" rule for any 4H candle.
- **S5 — Authorization (verbatim)**: "Iniciemos acá mismo" — build this now, in this session.
- **S6 — HTF grid resolution (user, via `AskUserQuestion`, 2026-11-12)**: the broker's H4 CSV is a fixed-UTC grid (00/04/08/12/16/20 UTC) — 09:00 NY never literally opens a candle on that grid (it's 13:00 or 14:00 UTC depending on DST, both inside the 12:00 UTC candle's own window). User chose **not** to build a new NY-anchored synthetic 4H aggregation (the "feature, not bugfix" pending item this would have revived) — instead, "the 9:00 model's HTF candle" is simply **the existing UTC-grid H4 candle whose window contains 09:00–10:30 NY**, which is always the 12:00 UTC candle (confirmed: both 13:00 and 14:00 UTC fall inside `[12:00, 16:00)`, so no DST branching is even needed to pick it) — and "the previous HTF candle" for the Turtle Soup check (S2) is simply `htf_candles[index-1]` on this same existing grid (the 08:00 UTC candle), not a session-semantic "5am candle." This is a deliberate precision trade-off, not a bug: less exact to Mado's literal 9am anchor, but reuses the existing H4 series as-is.

A genuine single-candle Turtle Soup (wick beyond the previous candle's high/low, close back inside it, same candle) needs its OWN direct two-candle comparison — not `CRTRange`/`_resolve`, which is built for a different, longer-unfolding resolution concept. T1 implements this directly.
  - The key-level-touch check reuses `alignment.htf_ltf._purge_wick_extremes` + `_key_level_credit_map` + `_purge_reaction`, evaluated immediately at the trigger candle (no deferred HTF search — the trigger candle's own CRTRange bounds are already known).
  - LTF confirmation reuses `entries.model1._track_anchor`/`_purge_signals` and `causal.retry_chain.chained_purge_engulf_signal`'s retry-on-invalidation logic, but the stop condition changes: no HTF true_break check is meaningful here (the HTF event already resolved as a one-shot false_break); the chain is bounded purely by the confirmation window (S4) instead.
