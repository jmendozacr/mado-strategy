# scanner-auto-execution

Objective: let the live scanner place real MT5 pending orders automatically for each new 1AM+9AM signal, instead of only sending a Telegram alert, gated by a configurable flag. Branch: `detector-key-level-reaction-probe` (current). Delivery: ask-on-risk. Test runner: `cd detector && .venv/Scripts/python.exe -m pytest` / `cd scanner && "D:\...\detector\.venv\Scripts\python.exe" -m pytest tests -q` (scanner's own venv is blocked by this machine's Device Guard policy, confirmed in `scanner-1am-9am-diversified.md` L5).

## Specs

- **S1 — User's request (verbatim)**: "Arranquemos con el flag de Python y la dejas de una vez en true porque vamos a comenzar a probar la estrategia a partir del domingo" — add an `AUTO_EXECUTE` flag, default `True`.
- **S2 — Why default `True` is acceptable now (user's own words)**: "No te preocupes que el domingo iniciamos en una cuenta de 10000 pero DEMO entonces no hay peligro" — Sunday's activation is on a $10,000 DEMO account, removing the real-money-loss risk this task's own earlier draft had flagged as the reason to default to `False`. The three ENGINEERING gaps raised before that decision (lot sizing, pending-order-type selection, failure handling) are unaffected by demo-vs-real and still had to be built — S2 only resolves the "is it safe to flip on" question, not "does the code exist yet."
- **S3 — Lot sizing**: derive real lot size from the live account balance (`mt5.account_info().balance`), a configured risk % (1.0, matching this session's own USD-ledger convention), the signal's own stop distance, and the SYMBOL's real tick value/size from MT5 (`mt5.symbol_info(symbol)`) — never a manual FX-rate conversion like the backtest's own research-only approximation (`odd/tasks/realistic-cost-prop-firm-validation.md`'s USDCAD pip-value derivation was for a historical cost estimate, not for real order sizing; MT5 already knows the real contract specs). Round DOWN to the symbol's `volume_step` (never up -- never risk more than the target %); if the rounded size is below `volume_min`, skip the trade entirely (log it) rather than force `volume_min`, which could silently risk far more than intended on a small account.
- **S4 — Order type**: a PENDING order (never a market order), matching `backtest.simulate`'s own fill model (`BacktestConfig.max_fill_wait=20` candles -- the backtest itself waits for price to return to `entry_price`, it never assumes instant fill). Compare `entry_price` to the CURRENT price at placement time: bullish + entry below current = BUY_LIMIT, bullish + entry above current = BUY_STOP; bearish + entry above current = SELL_LIMIT, bearish + entry below current = SELL_STOP. This single rule covers both `entry_type="wick"` and `"body"` signals without special-casing either (`entries/model1.py` confirms both occur in this pipeline's confirmed signals).
- **S5 — Pending-order expiry**: set the order's own MT5 expiration to `now + max_fill_wait * 15 minutes` (M15 candles) and let the broker auto-cancel it -- never a separate polling-based cancellation tracker, since MT5 already provides this natively (`ORDER_TIME_SPECIFIED` + `expiration`).
- **S6 — Failure handling**: a non-`TRADE_RETCODE_DONE` result from `order_send` is logged and skipped, never raised -- matches `main()`'s own existing per-poll `except Exception` philosophy (one symbol's order failure must never stop the whole poll loop or crash the scanner).
- **S7 — Flag**: `AUTO_EXECUTE = True` (module-level constant in `scanner/main.py`, same pattern as `SYMBOLS`/`POLL_SECONDS`) -- when `True`, `run_once` places the pending order AFTER sending the Telegram alert (alert always fires regardless of execution outcome, per S6); when `False`, behaves exactly as before this task (alert-only).
